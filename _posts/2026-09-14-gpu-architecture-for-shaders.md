셰이더 최적화 팁은 널려 있습니다. "분기를 피하라", "half를 쓰라", "텍스처 읽기를 줄여라". 문제는 이 팁들이 **왜** 맞는지, 그리고 **언제 틀리는지**를 함께 알려주는 경우가 드물다는 점입니다. 분기는 어떤 때는 공짜고 어떤 때는 셰이더 비용을 두 배로 만듭니다. 텍스처 읽기 하나가 어떤 때는 ALU 명령 100개보다 싸고 어떤 때는 프레임 전체의 병목이 됩니다. 이 차이를 설명하는 것은 팁이 아니라 **하드웨어의 구조**입니다.

이 글은 두 부분으로 되어 있습니다. 앞부분(1~4장)은 GPU가 실제로 어떻게 일을 처리하는지를 정리합니다. 실행 모델, 메모리 계층, 파이프라인, 그리고 모바일 GPU가 다른 점까지. 뒷부분(5장)은 그 구조에서 **논리적으로 따라오는** 셰이더 작성 원칙을 정리합니다. 특정 API나 엔진의 사용법이 아니라, 어느 플랫폼에서든 통하는 "하드웨어가 강요하는 것"에 무게를 둡니다.

## 1. CPU와 GPU는 다른 문제를 푼다

"GPU는 코어가 많다"는 설명은 절반만 맞습니다. 코어가 많은 건 결과이고, 원인은 **최적화 목표가 다르다**는 데 있습니다.

CPU는 **하나의 명령 흐름을 최대한 빨리 끝내는** 것이 목표입니다. 그래서 트랜지스터 예산의 대부분을 계산이 아닌 곳에 씁니다. 분기 예측기, 비순차 실행(out-of-order) 엔진, 거대한 캐시. 전부 "다음 명령이 데이터를 기다리며 멈추는 시간", 즉 **레이턴시를 줄이는** 장치입니다.

GPU는 **같은 프로그램을 수백만 번 돌리는** 것이 목표입니다. 4K 화면 한 장이 픽셀 830만 개고, 각 픽셀은 이웃 픽셀과 독립적으로 계산할 수 있습니다. 이런 문제에서는 한 스레드가 빨리 끝나는 것보다 **초당 처리량**이 중요합니다. 그래서 GPU는 정반대의 선택을 합니다. 레이턴시를 줄이는 장치를 거의 다 떼어내고, 그 자리에 연산 유닛을 채웁니다. 대신 레이턴시는 **숨깁니다**. 한 스레드 묶음이 메모리를 기다리는 동안 다른 묶음으로 갈아타는 방식으로요.

> **CPU는 레이턴시를 줄이고, GPU는 레이턴시를 숨긴다.** 셰이더 최적화의 원칙 대부분은 이 한 문장에서 파생됩니다.

이 선택은 셰이더 언어의 생김새에도 그대로 박혀 있습니다. 픽셀 셰이더에는 "옆 픽셀의 결과를 읽는" 문법이 없습니다(미분 명령이라는 좁은 예외가 있는데, 뒤에서 다룹니다). 스레드끼리 독립적이어야 하드웨어가 마음대로 스케줄할 수 있기 때문입니다. 셰이더가 "입력 → 출력"의 순수 함수 모양을 하는 것은 취향이 아니라 하드웨어의 요구입니다.

## 2. 실행 모델 — 스레드는 혼자 실행되지 않는다

### 2-1. 웨이브: 실제 실행 단위

셰이더 코드는 "픽셀 하나"의 관점으로 쓰지만, 하드웨어는 픽셀 하나를 실행하지 않습니다. **스레드 여러 개를 묶어 한 번에 같은 명령을 실행**합니다. 이 묶음을 NVIDIA는 워프(warp), AMD는 웨이브프론트(wavefront), 다른 곳에서는 웨이브·SIMD 그룹·서브그룹 등으로 부릅니다. 이 글에서는 **웨이브**로 통일합니다.

| 벤더 | 이름 | 폭 |
|---|---|---|
| NVIDIA | Warp | 32 |
| AMD GCN | Wavefront | 64 |
| AMD RDNA | Wave32 / Wave64 | 32 또는 64 |
| Intel Xe | SIMD8/16/32 | 8~32 (컴파일러가 선택) |
| Apple | SIMD-group | 32 |
| Arm Mali (Valhall 이후) | Warp | 16 |
| Qualcomm Adreno | Wave | 64 (일부 128) |

웨이브 하나에는 **명령 포인터가 하나**입니다. 즉 웨이브 안의 32개 스레드는 항상 같은 명령을 같은 순간에 실행합니다. 데이터만 다릅니다. 이것이 SIMT(Single Instruction, Multiple Threads) 모델입니다. 하드웨어 관점에서는 32레인 SIMD 벡터 연산이고, 프로그래머 관점에서는 32개의 스칼라 스레드처럼 보이게 포장한 것입니다.

이 포장이 새는 지점이 딱 하나 있습니다. **분기**입니다.

### 2-2. 분기 발산 — 양쪽을 다 실행한다

웨이브 안의 스레드들이 `if`에서 서로 다른 방향으로 가면 어떻게 될까요? 명령 포인터가 하나뿐이니 두 방향을 동시에 실행할 수는 없습니다. 하드웨어는 **양쪽을 차례로 실행**하고, 각 구간에서 해당하지 않는 스레드는 **실행 마스크**로 꺼둡니다.

```
웨이브 8레인, if (x > 0) { A } else { B }
x > 0 인 레인: ■   아닌 레인: □

               레인:  0 1 2 3 4 5 6 7
  A 실행 (마스크)     ■ ■ □ ■ □ □ ■ ■   ← 3개 레인은 놀고 있음
  B 실행 (마스크)     □ □ ■ □ ■ ■ □ □   ← 5개 레인은 놀고 있음
  ─────────────────────────────────
  총 비용 = A의 비용 + B의 비용
```

이걸 **발산(divergence)** 이라고 합니다. 발산한 분기의 비용은 "실행된 쪽"이 아니라 **양쪽의 합**입니다. 8개 레인 중 하나라도 다른 길로 가면 웨이브 전체가 그 길의 비용도 냅니다.

반대로 웨이브 안의 **모든** 스레드가 같은 방향이면 진짜로 한쪽만 실행됩니다. 이걸 **균일(uniform) 분기**라고 하고, 비용은 분기 명령 하나 수준으로 거의 공짜입니다. 여기서 실무적으로 중요한 구분이 나옵니다.

- 상수 버퍼 값, 셰이더 상수, 드로우 단위 플래그로 분기 → 웨이브 전체가 같은 값을 봅니다. **균일 분기, 공짜에 가깝습니다.**
- 텍스처 샘플 결과, 보간된 정점 속성, 픽셀 좌표로 분기 → 스레드마다 값이 다릅니다. **발산할 수 있습니다.**

두 번째 경우도 항상 발산하는 것은 아닙니다. 웨이브는 보통 화면상 인접한 픽셀들로 채워지기 때문에, 분기 조건이 **화면 공간에서 덩어리져** 있으면(그림자 안/밖, 머티리얼 영역 등) 대부분의 웨이브는 한쪽으로 몰립니다. 발산은 경계선에 걸린 웨이브에서만 일어납니다. 반면 노이즈 텍스처나 픽셀 단위로 바뀌는 값으로 분기하면 거의 모든 웨이브가 발산합니다.

루프도 같은 원리입니다. 스레드마다 반복 횟수가 다르면 웨이브는 **가장 오래 도는 스레드**가 끝날 때까지 계속 돌고, 먼저 끝난 스레드는 마스크된 채 기다립니다.

컴파일러도 이걸 알기 때문에 한 가지 선택을 합니다. 분기 양쪽이 짧으면 분기 자체를 없애고 **양쪽을 다 계산한 뒤 결과를 선택**(select)합니다. 분기 명령과 마스크 관리 비용보다 그냥 둘 다 계산하는 게 싸기 때문입니다. HLSL의 `[flatten]`/`[branch]` 속성은 이 선택을 강제하는 힌트입니다.

### 2-3. 레이턴시 숨기기와 점유율

앞서 GPU는 레이턴시를 "숨긴다"고 했습니다. 구체적으로는 이렇습니다.

VRAM에서 데이터를 가져오는 데는 **수백 사이클**이 걸립니다. 웨이브 A가 텍스처를 읽으라고 명령을 낸 뒤 결과를 기다려야 하면, 스케줄러는 A를 세워두고 **같은 연산 유닛에 상주하는 다른 웨이브 B, C, D**의 명령을 실행합니다. 이들이 돌아가는 동안 A의 데이터가 도착하고, A는 다시 실행 자격을 얻습니다. 웨이브가 충분히 많으면 연산 유닛은 한 번도 놀지 않습니다.

```
시간 →
웨이브 A: [ALU][ALU][LOAD.........................][ALU][ALU]
웨이브 B:           [ALU][ALU][LOAD.........................][ALU]
웨이브 C:                     [ALU][ALU][LOAD..................
웨이브 D:                               [ALU][ALU][LOAD.........
연산 유닛:  A    A    B    B    C    C    D    D    A    A    B   ← 계속 바쁨
```

그래서 **연산 유닛 하나에 몇 개의 웨이브가 상주할 수 있는가**가 성능을 좌우합니다. 이 비율을 **점유율(occupancy)** 이라고 합니다. 그리고 점유율을 결정하는 것은 크게 세 가지입니다.

1. **레지스터.** 연산 유닛의 레지스터 파일은 크기가 고정되어 있고, 상주하는 모든 웨이브가 이걸 **나눠 씁니다**. 셰이더 하나가 레지스터를 많이 쓰면 상주할 수 있는 웨이브 수가 줄어듭니다.
2. **공유 메모리(LDS / groupshared).** 컴퓨트 셰이더가 그룹 공유 메모리를 많이 쓰면 마찬가지로 상주 그룹 수가 줄어듭니다.
3. **하드웨어 상한.** 유닛당 최대 웨이브 수는 정해져 있습니다.

숫자로 감을 잡아 보겠습니다. AMD RDNA 2 기준으로 SIMD 하나는 VGPR(벡터 레지스터) 1024개를 갖고 있고, 최대 16개 웨이브가 상주할 수 있습니다.

| 셰이더의 VGPR 사용량 | 상주 가능한 웨이브 수 |
|---|---|
| 64개 이하 | 16 (최대) |
| 128개 | 8 |
| 256개 | 4 |

NVIDIA도 구조는 같습니다. SM 하나에 32비트 레지스터 65,536개가 있고 스레드 1,024~2,048개가 상주할 수 있으니(세대마다 다릅니다), 100% 점유율을 얻으려면 스레드당 레지스터를 32~64개 안에서 써야 합니다.

여기서 **레지스터 압박(register pressure)** 이라는 말이 나옵니다. 셰이더가 동시에 살려둬야 하는 값이 많으면 레지스터가 늘고, 레지스터가 늘면 점유율이 떨어지고, 점유율이 떨어지면 메모리 레이턴시를 숨길 웨이브가 부족해져 연산 유닛이 놀게 됩니다. 셰이더 프로파일러가 VGPR 개수를 제일 먼저 보여주는 이유입니다.

다만 점유율은 **수단이지 목표가 아닙니다.** 메모리 접근이 거의 없는 순수 계산 셰이더는 숨길 레이턴시가 없으니 낮은 점유율로도 연산 유닛을 꽉 채울 수 있습니다. 반대로 텍스처를 열 번 읽는 셰이더는 높은 점유율이 절실합니다. 그리고 웨이브 하나 안에서도 서로 의존하지 않는 명령이 연달아 있으면(텍스처 읽기 4개를 연속으로 낸 뒤 결과를 나중에 쓰는 식) 그 자체로 레이턴시가 겹칩니다. 점유율이 낮아도 이 **명령 수준 병렬성**으로 어느 정도 만회됩니다.

### 2-4. 균일한 값은 한 번만 계산된다

웨이브 안의 모든 스레드가 **같은 값**을 갖는 변수가 있습니다. 상수 버퍼에서 읽은 값, 드로우 인덱스, 그리고 그것들로만 계산한 결과. 이런 값을 32개 레인이 각자 계산하는 것은 낭비입니다.

그래서 AMD GPU에는 웨이브당 하나뿐인 **스칼라 유닛**과 스칼라 레지스터(SGPR)가 따로 있습니다. 컴파일러가 "이 값은 웨이브 안에서 균일하다"고 증명할 수 있으면 그 계산은 스칼라 유닛에서 **한 번만** 실행되고, 상수 버퍼 로드도 스칼라 로드 한 번으로 끝납니다. NVIDIA도 Turing부터 비슷한 **유니폼 데이터패스**를 갖고 있습니다.

이 구분은 코드에 그대로 드러납니다.

```hlsl
// g_ObjectIndex는 상수 버퍼 값 → 웨이브 균일 → 스칼라 로드 1회, 결과를 브로드캐스트
float4 tint = g_Tints[g_ObjectIndex];

// materialId는 정점 속성에서 보간된 값 → 스레드마다 다를 수 있음
// → 레인마다 벡터 로드. 최악의 경우 서로 다른 인덱스를 순서대로 처리하는 루프로 컴파일됨
float4 tint = g_Tints[materialId];
```

같은 한 줄이지만 비용은 전혀 다릅니다. 셰이더를 쓸 때 "이 값은 균일한가, 스레드마다 다른가"를 머릿속에서 구분하는 습관이 필요한 이유입니다. 균일한 계산은 아무리 복잡해도 거의 공짜고, 스레드별 계산은 아무리 간단해도 웨이브 전체의 비용입니다.

## 3. 메모리 — 계산은 싸고, 옮기는 것이 비싸다

### 3-1. 계층과 비용

GPU 메모리는 계층 구조이고, 계층을 하나 내려갈 때마다 레이턴시와 에너지가 한 자릿수씩 뛰는 것으로 생각하면 됩니다.

```
레지스터              수 사이클         스레드 전용
공유 메모리 (LDS)     ~수십 사이클       연산 유닛 안, 스레드 그룹이 공유
L1 / 텍스처 캐시      ~수십 사이클       연산 유닛 근처
L2 캐시               ~수백 사이클       칩 전체 공유
VRAM (GDDR/HBM)       수백 사이클 이상   칩 밖
```

숫자보다 중요한 것은 **비율**입니다. 32비트 부동소수점 곱셈 한 번과 DRAM에서 32비트를 읽어오는 것의 에너지 차이는 **백 배가 넘습니다**. 현대 GPU가 수십 TFLOPS를 낼 수 있는데 실제 셰이더가 그 근처에도 못 가는 이유는 대부분 연산 유닛이 데이터를 **기다리고** 있기 때문입니다.

대역폭도 마찬가지입니다. 데스크톱 GPU의 VRAM 대역폭은 수백 GB/s에서 1TB/s를 넘지만, 이걸 프레임 단위로 나누면 그리 넉넉하지 않습니다. 4K에서 RGBA16F 렌더 타깃 4장짜리 G-버퍼를 쓰고 다시 읽는 것만으로 프레임당 500MB가 넘고, 60fps면 그것만 30GB/s를 넘습니다. 여기에 텍스처, 그림자 맵, 포스트 프로세스 체인이 전부 얹힙니다. 모바일은 수십 GB/s를 CPU와 나눠 쓰는 데다 대역폭이 곧 **발열과 배터리**입니다.

> **셰이더 비용을 추정할 때 ALU 명령 수를 세는 것보다 "픽셀당 몇 바이트를 읽고 쓰는가"를 세는 것이 먼저다.**

### 3-2. 캐시 라인과 이웃

메모리는 바이트 단위로 오지 않습니다. **캐시 라인**(보통 64 또는 128바이트) 단위로 옵니다. 스레드 하나가 4바이트를 읽으면 나머지 60바이트는 캐시에 함께 올라옵니다. 이웃 스레드가 그 이웃 바이트를 읽으면 공짜고, 전혀 다른 곳을 읽으면 또 한 라인을 가져옵니다.

그래서 **인접한 스레드가 인접한 메모리를 읽는 것**이 GPU 메모리 접근의 제1원칙입니다. 이걸 코얼레싱(coalescing)이라고 합니다. 웨이브의 32개 스레드가 연속된 128바이트를 읽으면 트랜잭션 한 번, 32곳에 흩어진 4바이트를 읽으면 트랜잭션 32번입니다. 같은 "4바이트 읽기 한 줄"이 32배 차이가 납니다.

컴퓨트 셰이더에서 구조체 배열(AoS)보다 배열 구조체(SoA)가 자주 권장되는 이유가 이것입니다. 스레드들이 각 구조체의 `position`만 읽는다면, `position`들이 연속으로 붙어 있는 쪽이 캐시 라인을 꽉 채워 씁니다.

### 3-3. 텍스처 접근은 특별하다

텍스처 읽기는 "메모리 로드"와 다른 경로를 탑니다. **텍스처 유닛**이라는 전용 하드웨어가 주소 계산, 필터링, 포맷 디코딩, 블록 압축 해제를 맡습니다. 그리고 텍스처 메모리는 **2D 지역성을 위해 타일/스위즐 배치**로 저장됩니다. 선형 배치라면 텍스처의 아래 줄 텍셀은 위 줄에서 한 행 전체만큼 떨어져 있지만, 타일 배치에서는 가로세로로 인접한 텍셀들이 같은 캐시 라인에 들어갑니다.

이 구조가 요구하는 것이 하나 있습니다. **인접한 픽셀이 인접한 텍셀을 읽어야** 캐시가 효과를 냅니다. 여기서 밉맵의 진짜 이유가 나옵니다. 밉맵은 흔히 앨리어싱을 줄이는 용도로 설명되지만, 성능 면에서는 **텍셀과 픽셀의 비율을 1:1 근처로 유지해서 캐시 지역성을 지키는** 장치입니다. 밉맵 없이 멀리 있는 물체를 그리면 이웃 픽셀들이 텍스처상에서 수십 텍셀씩 떨어진 곳을 읽고, 캐시 라인마다 한 텍셀만 쓰고 버립니다.

텍스처와 관련해 알아야 할 하드웨어 사실이 하나 더 있습니다. 밉 레벨을 고르려면 UV가 이웃 픽셀에서 얼마나 변하는지, 즉 **미분값**이 필요한데, GPU는 이걸 **2×2 픽셀 쿼드 안에서 이웃 레인의 값을 빼서** 구합니다. `ddx`/`ddy`가 바로 이 명령입니다. 그런데 발산한 분기 안에서 텍스처를 샘플하면 쿼드의 이웃 레인이 꺼져 있을 수 있어 미분값이 정의되지 않습니다. 컴파일러가 거부하거나, 통과하더라도 경계에서 잘못된 밉 레벨이 나옵니다.

```hlsl
// 위험: 발산 가능한 분기 안의 암시적 밉 선택
if (useDetail)
    c = detailTex.Sample(s, uv);

// 안전: 미분값을 분기 밖에서 구하고 명시적으로 전달
float2 dx = ddx(uv), dy = ddy(uv);
if (useDetail)
    c = detailTex.SampleGrad(s, uv, dx, dy);   // 또는 SampleLevel
```

### 3-4. 쿼드와 헬퍼 레인

2×2 쿼드는 미분값 외에도 비용에 영향을 줍니다. 픽셀 셰이더는 **항상 쿼드 단위로 실행**됩니다. 삼각형이 쿼드의 픽셀 하나만 덮어도 쿼드 전체, 즉 4개 레인이 실행됩니다. 삼각형에 덮이지 않은 나머지 3개는 **헬퍼 레인**이라고 부르며, 미분값 계산을 위해 실행되지만 결과는 버려집니다.

삼각형이 크면 가장자리에서만 생기는 낭비라 무시할 수 있습니다. 하지만 삼각형이 픽셀 크기에 가까워지면 쿼드 효율은 25%까지 떨어집니다. 픽셀 셰이더 비용이 화면 픽셀 수의 **4배**가 될 수 있다는 뜻입니다. 이것이 "작은 삼각형이 많은 메시는 픽셀 셰이딩이 비싸다"의 정확한 이유고, UE5 Nanite가 아주 작은 삼각형을 하드웨어 래스터라이저 대신 컴퓨트 셰이더로 그리는 이유 중 하나입니다.

## 4. 파이프라인 — 고정 기능 사이에 끼인 셰이더

### 4-1. 셰이더는 파이프라인의 일부다

정점 셰이더와 픽셀 셰이더 사이에는 프로그래밍할 수 없는 **고정 기능** 단계들이 있습니다. 정점 페치, 프리미티브 조립, 클리핑, 래스터라이저, 뎁스 테스트, 블렌딩(ROP). 이 단계들은 처리량이 하드웨어로 정해져 있습니다. 래스터라이저는 클럭당 삼각형 몇 개, ROP는 클럭당 픽셀 몇 개.

```
정점 버퍼 → [정점 페치] → 정점 셰이더 → [프리미티브 조립·클리핑·래스터라이저]
         → [Early-Z] → 픽셀 셰이더 → [Late-Z·블렌딩·ROP] → 렌더 타깃

              [ ]: 고정 기능    나머지: 프로그래머블
```

이 구조에서 "병목"이란 **파이프라인의 어느 한 단계가 꽉 차서 앞뒤 단계가 기다리는 상태**입니다. 정점 셰이더가 병목이면 픽셀 셰이더를 아무리 줄여도 프레임 시간은 안 줄어듭니다. 래스터라이저가 병목(삼각형은 많은데 전부 작은 경우)이면 셰이더는 무관합니다. 그래서 최적화의 첫 단계는 항상 **어느 단계가 병목인지 찾는 것**이고, 셰이더 최적화는 그 답이 "셰이더"일 때만 의미가 있습니다.

### 4-2. Early-Z — 그리기 전에 버린다

뎁스 테스트는 원래 픽셀 셰이더 **뒤**에 있는 단계입니다. 하지만 셰이더가 뎁스를 바꾸지 않는다면 결과는 같으니, 하드웨어는 뎁스 테스트를 픽셀 셰이더 **앞**으로 옮겨 가려지는 픽셀의 셰이딩을 통째로 건너뜁니다. 이것이 Early-Z이고, 여기에 타일 단위로 뎁스 범위를 미리 비교하는 **계층적 Z**(Hi-Z)가 더해져 통째로 가려진 영역은 쿼드 단위로 걸러냅니다.

Early-Z가 효과를 내려면 두 조건이 필요합니다.

- **뎁스 버퍼에 이미 가까운 값이 쓰여 있어야** 합니다. 불투명 물체를 **앞에서 뒤로** 정렬해서 그리거나, 뎁스만 먼저 그리는 **뎁스 프리패스**를 두는 이유입니다.
- **픽셀 셰이더가 뎁스 결과에 영향을 주지 않아야** 합니다. 셰이더에서 `discard`/`clip`을 쓰거나 `SV_Depth`를 출력하면 "이 픽셀이 최종적으로 뎁스를 쓸지"를 셰이더가 끝나기 전엔 알 수 없으므로, 하드웨어는 Early-Z를 끄거나 뎁스 쓰기를 셰이더 뒤로 미룹니다. 알파 테스트 머티리얼이 불투명보다 비싼 이유입니다.

### 4-3. 모바일 GPU는 다르게 돈다 — TBDR

데스크톱 GPU는 **즉시 모드 렌더러**(IMR)입니다. 드로우 명령이 오면 삼각형을 바로 래스터라이즈하고 셰이딩해서 VRAM의 프레임버퍼에 씁니다. 뎁스 테스트도, 블렌딩도 VRAM을 읽고 씁니다. 대역폭을 많이 쓰지만 데스크톱은 그럴 여유가 있습니다.

모바일은 여유가 없습니다. 대역폭이 곧 전력이기 때문입니다. 그래서 모바일 GPU(Arm Mali, Qualcomm Adreno, Apple, PowerVR)는 **타일 기반 렌더링**을 씁니다. 렌더패스 하나를 두 단계로 쪼갭니다.

```
[1단계: 비닝]  렌더패스의 모든 드로우에 대해 정점 셰이더 실행
              → 변환된 삼각형을 화면 타일별 목록에 분류
                (타일 크기는 하드웨어마다 16×16에서 수백 픽셀까지 다양)
              → 목록과 정점 출력은 메모리에 저장

[2단계: 타일별 렌더링]  타일마다:
              온칩 타일 메모리에 컬러/뎁스 로드(또는 클리어)
              → 그 타일에 걸친 삼각형만 래스터·픽셀 셰이딩 (뎁스·블렌딩은 전부 온칩)
              → 타일이 끝나면 결과를 VRAM에 한 번 저장(resolve)
```

핵심은 2단계입니다. **한 타일이 렌더패스 끝까지 온칩에서 처리**되므로, 오버드로우가 열 번 일어나도 VRAM 쓰기는 타일당 한 번입니다. 뎁스 버퍼는 밖에서 안 쓴다면 **VRAM에 아예 쓰지 않아도 됩니다**.

여기서 몇 가지 결정적인 함의가 나옵니다.

| 데스크톱(IMR)에서는 | 모바일(TBDR)에서는 |
|---|---|
| 렌더 타깃 전환은 상태 변경 비용 정도 | 렌더패스 경계마다 **타일 전체를 VRAM에 쓰고 다시 읽음**. 가장 비싼 작업 중 하나 |
| 프레임버퍼를 읽으려면 텍스처로 복사 | 같은 렌더패스 안에서는 타일 메모리를 직접 읽을 수 있음(서브패스, framebuffer fetch) |
| 정점 출력은 온칩에서 픽셀 셰이더로 | 정점 출력이 **메모리에 저장**됨. 보간자 개수가 곧 대역폭 |
| 불투명 정렬은 Early-Z 효율 문제 | Apple/PowerVR의 HSR은 **순서와 무관하게** 가려진 픽셀을 제거 |
| 뎁스/스텐실은 항상 VRAM에 존재 | `storeOp = DONT_CARE`, 메모리리스 텍스처로 **VRAM 할당 자체를 생략** 가능 |

마지막 두 줄을 보면 TBDR이 유리해 보이지만, 조건이 있습니다. 가려진 픽셀의 셰이딩을 건너뛰는 장치들(Apple/PowerVR의 HSR, Arm의 FPK, Adreno의 LRZ)은 모두 "이 픽셀이 최종적으로 보일지"를 셰이더 실행 **전에** 알 수 있어야 동작합니다. `discard`, 알파 블렌딩, 셰이더 뎁스 출력은 그 전제를 깨뜨립니다. 데스크톱에서 Early-Z를 깨는 것과 같은 목록이지만, 모바일에서는 손해가 더 큽니다.

## 5. 그래서, 셰이더를 쓸 때 무엇을 고려해야 하나

지금까지의 하드웨어 사실에서 원칙을 하나씩 뽑아 보겠습니다. 형식은 **"하드웨어가 이렇게 생겼으므로 → 이렇게 한다"** 입니다.

### 5-1. 분기: 균일하게 만들거나, 짧게 만든다

**사실:** 발산한 분기는 양쪽 비용을 모두 낸다. 균일 분기는 거의 공짜다. (2-2절)

- 분기 조건을 **상수 버퍼·드로우 단위 값**으로 옮길 수 있으면 옮깁니다. 머티리얼 플래그, 기능 토글, 품질 단계는 픽셀별 값이 아니라 균일 값입니다.
- 픽셀별 값으로 분기해야 한다면 **양쪽이 짧은지** 확인합니다. 짧으면 컴파일러가 select로 바꾸어 발산 비용이 없습니다. 길다면 조건이 화면 공간에서 덩어리져 있는지(대부분의 웨이브가 한쪽으로 몰리는지) 생각합니다.
- 스레드마다 반복 횟수가 다른 루프는 웨이브가 **최대 반복 횟수**만큼 돕니다. 반복 횟수 상한을 낮추거나 균일하게 만듭니다.
- 셰이더 변형(permutation) 폭발을 막기 위해 균일 분기로 대체하는 것은 좋은 전략입니다. 다만 한 가지를 기억해야 합니다. **레지스터는 실행되지 않는 분기 쪽까지 포함해 최악 경로 기준으로 할당**됩니다. 균일 분기로 열 가지 기능을 한 셰이더에 넣으면 실행 비용은 없어도 점유율은 가장 무거운 경로에 맞춰 떨어집니다.

```hlsl
// 균일: 거의 공짜. 변형을 줄이는 용도로 적극 사용
if (g_Material.useNormalMap) { ... }

// 픽셀별, 양쪽 짧음: 컴파일러가 select로 바꿈. 걱정할 필요 없음
float3 c = (ndotl > 0.0) ? lit : ambient;

// 픽셀별, 양쪽 길고 조건이 노이즈처럼 흩어짐: 실제 발산. 구조를 다시 생각할 것
if (noise.r > 0.5) { /* 50줄 */ } else { /* 다른 50줄 */ }
```

### 5-2. 레지스터: 살아 있는 값의 개수를 의식한다

**사실:** 레지스터 사용량이 점유율을 정하고, 점유율이 레이턴시를 숨길 능력을 정한다. (2-3절)

- 컴파일러 출력에서 **VGPR 수와 점유율을 확인하는 습관**을 들입니다. Radeon GPU Analyzer, Nsight, Mali Offline Compiler, Xcode의 셰이더 프로파일러가 모두 보여줍니다. 숫자를 보지 않고 "이 정도면 가볍겠지"라고 짐작하는 것이 가장 흔한 실수입니다.
- 레지스터는 **동시에 살아 있는 값의 최대 개수**입니다. 텍스처 8장을 위에서 다 읽어두고 아래에서 조합하는 구조는 레이턴시는 잘 겹치지만 결과 8개가 동시에 살아 있습니다. 읽고-쓰고-버리는 구조로 바꾸면 레지스터는 줄지만 레이턴시는 덜 겹칩니다. 둘 사이의 균형은 프로파일러 숫자로 결정합니다.
- **동적으로 인덱싱되는 로컬 배열**은 레지스터에 올릴 수 없어 스크래치 메모리(VRAM)로 나가는 경우가 많습니다. 성능이 갑자기 몇 배 나빠졌다면 첫 번째 용의자입니다. 크기가 작고 인덱스가 컴파일 시점에 풀리도록 `[unroll]`하거나, 상수 버퍼·구조화 버퍼로 옮깁니다.
- **낮은 정밀도**는 레지스터를 절반으로 줍니다. 5-3에서 이어서 다룹니다.

```hlsl
// 스크래치로 나갈 가능성이 높은 패턴
float weights[32];
for (int i = 0; i < count; ++i)      // count가 런타임 값이면 인덱스가 풀리지 않음
    weights[i] = ...;
```

### 5-3. 정밀도: 필요한 만큼만 쓴다

**사실:** 16비트 값은 레지스터를 절반만 쓰고, 대부분의 GPU에서 ALU 처리량이 두 배다. 모바일 GPU에서 이 차이는 더 크다. (2-3절, 3-1절)

| 용도 | 권장 정밀도 | 이유 |
|---|---|---|
| 색, 알베도, 라이팅 중간값 | 16비트 | 눈이 구분하는 범위를 넉넉히 넘음 |
| 노멀, 탄젠트 (정규화된 벡터) | 16비트 | 방향 표현에는 충분. 단 정규화 직전의 큰 값은 주의 |
| UV | 상황에 따라 | 큰 텍스처를 타일링하는 UV는 16비트로 부족. 정밀도 부족은 "떨림"으로 나타남 |
| 월드 좌표, 뎁스, 뷰 공간 위치 | 32비트 | 범위가 크고 차이가 작음. 16비트로 하면 즉시 아티팩트 |
| 루프 카운터, 인덱스 | 32비트 정수 | 정수는 정밀도 문제와 다른 얘기 |

- 모바일 셰이더는 `mediump`(GLSL)/`half`(Metal)를 **기본값**으로 두고 필요한 곳만 `highp`/`float`로 올리는 쪽이 맞습니다. 데스크톱은 `min16float` 또는 16비트 타입 활성화 옵션으로 접근합니다. HLSL의 `half`는 옵션을 켜지 않으면 그냥 `float`입니다.
- 16비트와 32비트를 섞으면 **변환 명령**이 들어갑니다. 한 식 안에서 자주 왔다갔다하면 절약한 것보다 변환에 더 쓸 수 있습니다. 정밀도는 함수 단위, 파이프라인 구간 단위로 통일합니다.

### 5-4. 메모리: 적게 읽고, 이웃과 함께 읽고, 압축해서 읽는다

**사실:** 데이터를 옮기는 비용이 계산 비용을 압도한다. 캐시 라인 단위로 오고, 텍스처는 2D 지역성에 최적화되어 있다. (3장)

- **픽셀당 바이트 예산**을 계산합니다. 렌더 타깃 포맷은 필요한 최소로. RGBA16F가 필요한지 R11G11B10F로 되는지, 노멀은 옥타헤드럴 인코딩으로 2채널에 넣을 수 있는지. G-버퍼 설계는 "무엇을 저장할까"보다 "몇 바이트에 넣을까"의 문제입니다.
- **텍스처는 항상 블록 압축**(BC/ASTC/ETC)으로, **항상 밉맵**과 함께. 압축 텍스처는 캐시 라인 하나에 텍셀이 4~8배 더 들어갑니다. 밉맵 없는 텍스처는 멀리 있을 때 캐시를 스래싱합니다.
- **채널을 패킹**합니다. 러프니스·메탈릭·AO를 각각 R8 텍스처 3장으로 두면 페치 3번, RGB 한 장이면 1번입니다.
- **종속 텍스처 읽기**(한 텍스처의 결과로 다른 텍스처의 UV를 정하는 것)는 두 읽기의 레이턴시가 겹치지 못하고 직렬로 쌓입니다. 피할 수 없으면 최소화합니다.
- **상수 버퍼와 구조화 버퍼를 용도에 맞게** 씁니다. 웨이브 전체가 같은 위치를 읽으면 상수 버퍼(스칼라 로드 한 번), 스레드마다 다른 인덱스면 구조화 버퍼나 텍스처. 상수 버퍼를 스레드별 인덱스로 뒤지는 것은 두 세계의 나쁜 점만 얻습니다.
- 컴퓨트 셰이더에서는 **스레드 인덱스와 메모리 주소의 대응**을 설계합니다. 연속 스레드가 연속 주소를 읽는지, 2D 이미지를 처리할 때 스레드 그룹의 모양이 텍스처 캐시의 타일 모양과 맞는지.

### 5-5. 계산 대 조회: 요즘은 계산이 더 싸다

**사실:** ALU는 남고 대역폭과 레이턴시는 부족하다. (3-1절)

10년 전에는 `sin`, `pow`, 복잡한 함수를 룩업 텍스처로 대체하는 것이 정석이었습니다. 지금은 대체로 **반대**입니다. 연산 유닛은 유휴 상태인 경우가 많고, 텍스처 읽기 하나는 수백 사이클의 레이턴시와 캐시 라인 하나를 소모합니다. 노이즈 함수, 색 공간 변환, 간단한 커브 정도는 **계산하는 쪽이 빠른** 경우가 많습니다.

물론 예외가 있습니다. 적분이 들어간 BRDF 사전 계산 테이블처럼 계산으로는 도저히 안 되는 것, 그리고 이미 다른 이유로 읽고 있는 텍스처에 채널이 남는 경우. 판단 기준은 **산술 밀도**(arithmetic intensity), 즉 바이트 하나를 읽어올 때 그 바이트로 몇 번의 연산을 하는가입니다. 이 값이 낮은 셰이더는 대역폭 바운드고, 그런 셰이더에서 텍스처를 추가하는 것은 병목을 키우는 일입니다.

### 5-6. 파이프라인 단계: 일은 가능한 앞으로, Early-Z는 지킨다

**사실:** 픽셀은 정점보다 훨씬 많고, 정점은 드로우보다 훨씬 많다. 가려진 픽셀은 Early-Z가 공짜로 버려 준다. (4장)

- **픽셀 셰이더의 계산이 정점 셰이더로 갈 수 있는지** 확인합니다. 선형으로 보간해도 되는 값(월드 위치, UV 변환, 라이트 방향의 일부)은 정점에서 계산하고 보간자로 넘깁니다. 단, 보간자 개수 자체가 비용(특히 TBDR에서 대역폭)이므로 "정점당 계산 vs 보간자 하나 추가"를 저울질합니다.
- **정점 셰이더의 계산이 CPU나 컴퓨트로 갈 수 있는지** 확인합니다. 모델·뷰·프로젝션 행렬은 곱해서 하나로 넘깁니다. 정점 셰이더에서 행렬 세 개를 곱하는 것은 그 곱셈을 정점 수만큼 반복하는 것입니다.
- **Early-Z를 지킵니다.** 불투명은 앞에서 뒤로 정렬하거나 뎁스 프리패스를 둡니다. `discard`가 필요한 알파 테스트 머티리얼은 불투명 다음에 따로 그립니다. `SV_Depth` 출력은 정말 필요한 곳(파랄랙스, 임포스터)에만 쓰고, 가능하면 보수적 뎁스(`SV_DepthGreaterEqual` 등)로 Early-Z를 일부 살립니다.
- **오버드로우**는 픽셀 셰이더 비용을 곱해 버립니다. 반투명 파티클처럼 겹침이 심한 것은 낮은 해상도 타깃에 그린 뒤 업샘플하는 것이 정석입니다. 풀스크린 패스는 셰이더 하나가 화면 전체를 한 번 셰이딩하는 것과 같으니, 패스 수 자체가 비용입니다.

### 5-7. 컴퓨트 셰이더: 그룹은 웨이브의 배수로, 공유 메모리는 예산 안에서

**사실:** 스레드 그룹은 웨이브 단위로 쪼개지고, 공유 메모리는 점유율을 제한하며, 웨이브 안의 통신은 공유 메모리 없이도 된다. (2장)

- **스레드 그룹 크기는 64의 배수**가 안전합니다. 32와 64 양쪽의 배수라 어느 하드웨어에서도 웨이브가 반쯤 빈 채로 돌지 않습니다. 2D 작업이면 8×8이 기본값입니다.
- `groupshared` 메모리는 레이턴시가 낮지만 **그룹당 사용량이 곧 상주 그룹 수의 상한**입니다. 크게 잡으면 점유율이 떨어집니다. 또 보통 32개 뱅크에 4바이트 단위로 배치되어 있어, 같은 뱅크의 다른 주소를 동시에 치면(뱅크 충돌) 직렬화됩니다. 스트라이드가 32의 배수인 접근 패턴이 대표적인 함정입니다.
- **웨이브 내장 함수**(HLSL `WaveActiveSum`, `QuadReadAcrossX` 등, GLSL 서브그룹 연산)는 공유 메모리와 배리어 없이 웨이브 안에서 값을 교환합니다. 리덕션, 프리픽스 합, 이웃 값 참조에 먼저 고려합니다.
- **같은 주소에 대한 원자 연산**은 하드웨어가 순서대로 처리하므로 스레드 수만큼 직렬화됩니다. 웨이브 안에서 먼저 합치고 웨이브당 한 번만 원자 연산을 내는 패턴이 기본입니다.

```hlsl
// 나쁨: 웨이브 32개 레인이 같은 주소에 32번 원자 연산
InterlockedAdd(g_Counter[0], myCount);

// 좋음: 웨이브 안에서 합친 뒤 한 레인만 원자 연산
uint waveTotal = WaveActiveSum(myCount);
if (WaveIsFirstLane())
    InterlockedAdd(g_Counter[0], waveTotal);
```

### 5-8. 모바일(TBDR)이라면 추가로

**사실:** 타일 메모리를 VRAM에 쓰고 읽는 것이 가장 비싸고, 정점 출력이 메모리를 거치며, 은면 제거는 셰이더가 뎁스에 관여하지 않을 때만 동작한다. (4-3절)

- **렌더패스 경계를 최소화**합니다. 렌더 타깃을 바꾸는 것은 데스크톱에서는 상태 변경이지만 모바일에서는 타일 전체의 저장과 재로드입니다. 프레임 중간에 "잠깐 다른 타깃에 그리고 돌아오기"가 가장 흔한 손실입니다.
- **로드·스토어 연산을 정직하게 지정**합니다. 이전 내용이 필요 없으면 `LOAD_OP_CLEAR`나 `DONT_CARE`, 렌더패스 밖에서 안 쓸 어태치먼트(대부분의 뎁스)는 `STORE_OP_DONT_CARE`. Vulkan은 transient 어태치먼트와 lazily allocated 메모리, Metal은 memoryless 스토리지 모드로 VRAM 할당까지 없앨 수 있습니다.

```cpp
// 뎁스를 이 렌더패스 밖에서 읽지 않는다면
depth.loadOp  = VK_ATTACHMENT_LOAD_OP_CLEAR;
depth.storeOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;   // 타일 → VRAM 쓰기 자체가 사라짐
```

- **프레임버퍼를 읽어야 하는 작업**(디퍼드 라이팅, 소프트 파티클, 프로그래머블 블렌딩)은 서브패스나 framebuffer fetch로 **같은 렌더패스 안에서** 처리합니다. 타일 메모리를 읽는 것은 공짜에 가깝고, 텍스처로 다시 읽는 것은 타일 저장을 강제합니다.
- **정점 출력 크기를 줄입니다.** 보간자 하나하나가 비닝 단계에서 메모리에 써지고 다시 읽힙니다. 정점 속성도 16비트 노멀, 압축 UV처럼 작게 유지합니다.
- **`discard`와 알파 테스트를 최소화**합니다. 은면 제거를 무력화해 가려질 픽셀까지 셰이딩하게 됩니다. 불가피하면 불투명을 모두 그린 뒤에 그립니다.
- **16비트 정밀도가 기본**입니다. 모바일 GPU는 fp16 처리량이 fp32의 두 배이고 레지스터 절약 효과도 더 크게 나타납니다.

### 5-9. 측정하지 않은 최적화는 최적화가 아니다

**사실:** 병목은 파이프라인 단계 중 하나에 있고, 그 단계가 아닌 곳을 줄이면 아무 일도 일어나지 않는다. (4-1절)

간단한 실험만으로도 병목을 좁힐 수 있습니다.

| 실험 | 프레임 시간이 크게 줄면 |
|---|---|
| 렌더 해상도를 절반으로 | 픽셀 셰이더 또는 대역폭 바운드 |
| 텍스처 해상도를 극단적으로 낮춤 (밉 바이어스) | 텍스처 대역폭 바운드 |
| 픽셀 셰이더를 단색 출력으로 교체 | 픽셀 셰이더 ALU 바운드 |
| 정점 수를 줄임 (LOD 강제) | 정점 셰이더 또는 래스터 바운드 |
| 드로우 수를 줄임 | CPU 또는 드라이버 바운드 ([배칭 글](/graphics/2026/08/20/batching.html) 참고) |

그 다음은 도구입니다. RenderDoc, PIX, Nsight Graphics, Radeon GPU Profiler, Xcode Metal 디버거, Arm Streamline, Snapdragon Profiler. 이름은 다르지만 보는 것은 비슷합니다. **VGPR 수와 점유율, 웨이브 수, 캐시 히트율, ALU/텍스처 유닛 사용률, 각 패스의 시간.**

그리고 하드웨어마다 답이 다릅니다. 데스크톱에서 이득인 것이 모바일에서 손해일 수 있고(렌더 타깃 전환), NVIDIA에서 무해한 것이 AMD에서 문제가 될 수 있습니다(웨이브 크기가 다르니 발산 양상도 다릅니다). 목표 플랫폼에서 측정한 숫자만 믿습니다.

## 6. 한 장 정리

| 하드웨어 사실 | 따라오는 원칙 |
|---|---|
| 스레드는 웨이브 단위로 같은 명령을 실행한다 | 분기 조건은 균일하게. 발산하는 분기는 짧게 |
| 균일한 값은 스칼라 유닛에서 한 번만 계산된다 | 상수 기반 계산은 공짜, 스레드별 계산만 아낀다 |
| 레지스터 파일을 상주 웨이브가 나눠 쓴다 | 동시에 살아 있는 값을 줄이고, VGPR 수를 확인한다 |
| 레이턴시는 다른 웨이브로 갈아타서 숨긴다 | 점유율을 확보한다. 단 ALU 바운드면 덜 중요 |
| 데이터 이동이 계산보다 백 배 비싸다 | 픽셀당 바이트를 세고, 계산으로 대체할 수 있으면 계산한다 |
| 메모리는 캐시 라인 단위로 온다 | 이웃 스레드가 이웃 주소를 읽게 한다 |
| 텍스처는 2D 타일 배치, 미분값은 쿼드에서 나온다 | 밉맵과 압축을 항상 쓰고, 분기 안 샘플은 명시적 미분값으로 |
| 픽셀 셰이더는 2×2 쿼드 단위로 돈다 | 픽셀보다 작은 삼각형을 피한다 |
| 뎁스 테스트는 셰이더 앞으로 당길 수 있다 | 앞→뒤 정렬 또는 프리패스, discard와 뎁스 출력 최소화 |
| 모바일은 타일 단위로 온칩에서 그린다 | 렌더패스 경계 최소화, 로드·스토어 정직하게, 프레임버퍼는 서브패스로 읽기 |
| 병목은 한 단계에 있다 | 먼저 어느 단계인지 측정한다 |

## 마치며

GPU는 **"같은 일을 많이"** 하도록 설계된 기계입니다. 스레드를 묶어 같은 명령을 실행하고, 같은 값은 한 번만 계산하고, 이웃한 데이터를 한 번에 가져오고, 기다리는 동안 다른 묶음을 돌립니다. 이 설계가 잘 맞는 일에서는 CPU의 수십 배를 내고, 안 맞는 일에서는 그 이점이 전부 사라집니다.

그래서 셰이더 최적화의 대부분은 새로운 기법을 넣는 것이 아니라, **하드웨어가 이미 잘하는 방식에 일을 맞춰주는 것**입니다. 균일하게, 연속적으로, 작게, 그리고 파이프라인의 앞 단계에서. 팁을 외우는 것보다 "이 코드가 웨이브 단위로 어떻게 실행될까, 몇 바이트를 읽을까, 어느 단계에서 돌까"를 상상할 수 있는 것이 훨씬 오래 갑니다.

> **셰이더는 픽셀 하나의 관점으로 쓰되, 비용은 웨이브와 캐시 라인과 타일의 관점으로 셀 것.**
